# v1.5.0 — Private operator intelligence (design backlog only)

**Added October 22, 2026; not part of the v1.1.0 release or public site.**
The owner has requested that sensitive operational analytics be delivered privately in Discord DMs, **not** broadcast in the shared WARDOGS channels. The admin suspicious-play workflow requires separate owner/Dan review and source validation before implementation.

## 1. Dan-only operations brief (Discord DM)

- Recipient: Dan's **verified, explicitly authorized Discord account**, never a public channel or generic role mention.
- Distribution: private bot DM only after a narrowly scoped Discord Application is approved and DM delivery validated; a webhook cannot DM a user.
- Outputs: concise private summary graphic/table plus a sanitized CSV attachment (and optionally XLSX).
- Contents, subject to complete WARCON coverage: captured completed-match starts by Eastern hour/day, top *recorded* start windows, actual peak-players values if source fields are reliable, time-of-day/faction comparisons with denominators, capture gaps, and broadcast-overlap annotations only when the broadcast feed is validated.
- **Broadcast notation:** a small red center dot or unobtrusive outline on captured activity heatmap cells where verified WARDOGS/WARCON broadcast intervals overlap. Establish actual broadcast start/end fields, data source and retention before claiming overlap. An RCON/console broadcast whisper is NOT itself proof a streamer was live. Flag streams from verified scheduling/status only; do not infer a stream from server population spikes.
- Do not publish full "best launch windows", performance lift attributable to streams, staffing/operational strategy, or comparative broadcast analysis on the public 1ADAAR site. Public v1.1.0 summary is limited to counts derived from the already visible public heatmap.
- Do not claim causality from correlation; support defensible matched-window comparisons, sample sizes, uncertainties and missing coverage.
- If bot DM delivery fails because DMs are closed, hold the private report and notify the owner of a delivery failure through an approved secure channel; **never fall back to a public Discord channel**.

## 2. Owner/admin-only suspicious-play evidence brief (Discord DM)

- Recipient: the owner's authenticated Discord account, via the separately authorized bot, not a public guild channel.
- Attachments: XLSX workbook with Source, Matches, Player Events (when actually captured), Aggregates, Heuristics, Data Quality, Review Notes, Audit Log; companion machine-readable CSV; optional evidence-only image/PDF summary if approved.
- Capture/source provenance: precise source endpoint, capture timestamp/timezone, server ID, map, match ID, player identity token when lawfully accessible, faction, recorded kills/deaths, time played and whether a match report reflects the full game or only the final faction/segment.
- **Key hypothesis to investigate, not assume:** faction changes may distort per-match public reports that aggregate only a final team membership. Determine whether the WARCON public endpoint actually does this. Public match K/D alone cannot prove intentional manipulation or cheating.
- Potential flags: high outlier K/D over meaningful sample sizes, abrupt shifts, frequent faction switches *only if observed*, implausible kill rates *only when reliable elapsed time exists*, persistent extremes across verified comparable servers, and missing/contradictory data segments.
- Document exact triggers, denominators, source completeness, sample sizes, confidence levels and benign alternative explanations. Distinguish anomalies from evidence of misconduct; **never auto-ban, publicly label someone a cheater or accuse a user based on a statistical anomaly**.
- No unauthorized cross-server scraping, raw SteamID publication, collection of protected player records, or unverified player identity joins. Apply minimal retention, private files, access controls and explicit delete/revoke process.
- Any request to escalate a serious, source-supported anomaly to a WARDOGS admin channel needs owner/Dan approval and a minimal factual redacted summary; avoid exposing the full evidence book in public.
- Optional LLM narrative can explain why rules fired and propose follow-up questions, but must quote the local computed evidence and cannot create evidence or turn speculation into findings. Keep calculations deterministic and auditable.

## 3. Discord integration requirements

- Discord DMs with attachments require a Discord bot/Application with proper guild installation or direct-user authorization, permissions, DM settings and a secure token—not a webhook.
- Use only owner-approved Discord account IDs stored as Actions/edge secrets. Avoid exposing IDs in Pages bundles. The bot must send privately with explicit destination checks before attachments.
- Plan for CSV formula-injection-safe quoting/escaping and XLSX document hardening. Validate attachment size limitations at runtime and never send a truncated data export as complete.
- Scheduled reporting from GitHub Actions may call a narrowly scoped secure bot API if eligible, but credentials and data must remain private; no persistent machine on the owner's PC or paid hosting by default.
- Prepare a manual dry-run to the operator account, review evidence and opt-in channel policies, then enable recurring jobs separately after Dan approves the delivery method.

**Ship now (v1.1.0):** six-hour 24H heatmap markers, all 24 hourly slots, a public basic captured-start summary beside the heatmap, clear no-data state, and normal public WARCON result views.

The v1.1.1 real-data-only public cleanup remains its own branch/release.
